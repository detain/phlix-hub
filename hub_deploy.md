# `@phlix/ui` asset-rebuild runbook — phlix-hub

> **What this file is.** Despite the `*_deploy.md` name, this is *not* a general hub-deployment
> guide — it is the runbook for updating the `@phlix/ui` npm dependency and rebuilding the hub's
> Vite SPA bundle under `public/assets/app/`. For provisioning the hub itself (systemd unit, env
> file, TLS, first boot) use **README.md** and the idempotent **`scripts/install.sh`** (which
> owns `/opt/phlix-hub`, `/etc/phlix-hub.env` and the `phlix-hub.service` unit — running
> `scripts/install.sh --update` is the sanctioned way to take a managed host forward, and it
> even migrates legacy systemd units that still exec `public/index.php`). All hosts below are
> placeholders — fill in your own.

## Two-Level Architecture

`@phlix/ui` is published as a **GitHub archive tarball pinned by tag** in `web-ui/package.json`.
The hub's `web-ui/` imports it and runs `vite build` to produce **Vite code-split chunks** in
`public/assets/app/assets/`. The hub's Workerman HTTP worker serves these committed assets
directly.

```
@phlix/ui npm package (dist/phlix-ui.js, dist/player.js, ...)
        ↓  npm ci (tarball pinned by tag in package.json, sha512 integrity in package-lock.json)
phlix-hub/web-ui/node_modules/@phlix/ui/
        ↓  vite build
phlix-hub/public/assets/app/assets/    ←  committed to git, served by hub Workerman
```

Because the bundle under `public/assets/app/` is git-tracked, every ui bump lands as **two
coupled commits-worth of changes**: the `web-ui/package.json` + `web-ui/package-lock.json` pin,
and the rebuilt asset tree. CI has pin-skew tripwires
(`scripts/report-ui-pin-skew.php`, wired in `.github/workflows/ci.yml`) that flag a lock pin
whose installed `@phlix/ui` version diverges from what the committed bundle was built against —
so build the bundle in the same change as the pin bump.

## Prerequisites

- SSH access to the hub host **as a non-root deploy user** with `sudo` for `systemctl`
  (`deploy@example.net` below — substitute your own)
- `npm` on the build machine (local or server)
- `rsync` if you build locally and sync assets up

## Hub-Specific Env

The hub requires `HUB_JWT_SECRET` to start, read from `/etc/phlix-hub.env` (the
`EnvironmentFile` of the `phlix-hub.service` unit). Since R14-08 the boot pre-flight **also
refuses documented placeholder secrets** (`CHANGE-ME-run-openssl-rand-hex-32`, `change-me`,
`your-secret-here`, …) with `exit 1` — see README §Installation (manual) for the exact
semantics.

**Hub directories on the live server (paths as generated by `scripts/install.sh`):**

- Hub code: `/opt/phlix-hub/`
- Built web assets: `/opt/phlix-hub/public/assets/app/assets/`
- Hub env file: `/etc/phlix-hub.env` (mode 600; not readable by ordinary users)
- Hub logs: `/opt/phlix-hub/.logs/`

## Deploy Steps

### Option A — Build locally, sync to server

**1. Build `@phlix/ui` (only if you made source changes there):**

```bash
cd /path/to/phlix-ui
npm run build
git add dist/
git commit -m "chore(phlix-ui): bump to vX.Y.Z"
git tag vX.Y.Z
git push && git push --tags
```

**2. Point the hub at the new tag in `web-ui/package.json`:**

```json
"@phlix/ui": "https://github.com/detain/phlix-ui/archive/refs/tags/vX.Y.Z.tar.gz"
```

Tag-form archive URL only — `refs/heads/master` URLs would float and the lockfile integrity hash
would churn on unrelated commits.

**3. Regenerate the lock entry, then build the hub web-ui:**

```bash
cd /path/to/phlix-hub/web-ui
NPM_CONFIG_USERCONFIG=/dev/null npm install   # rewrites the @phlix/ui resolved+sha512 integrity
NPM_CONFIG_USERCONFIG=/dev/null npm ci        # verifies the lock byte-matches the tarball
npm run build
```

The integrity recipe that matters: `npm install` records the tarball's `sha512` in
`package-lock.json` (`packages.node_modules/@phlix/ui.integrity`); every later `npm ci` (local,
CI, and on the server) **fails loudly** if the downloaded tarball doesn't hash to it. That is
what pins supply-chain bytes for a git-archive dependency — commit `package.json` and
`package-lock.json` **together**, never one without the other.

**4. Sync built assets to the live hub:**

```bash
rsync -av --delete \
  /path/to/phlix-hub/public/assets/app/assets/ \
  deploy@example.net:/opt/phlix-hub/public/assets/app/assets/
```

(Prefer committing the rebuilt asset tree in the same branch and letting the server `git pull` —
Option B — so what you serve is what's in git.)

**5. Verify chunk names landed:**

```bash
ssh deploy@example.net "ls /opt/phlix-hub/public/assets/app/assets/index-*.js"
```

The SPA shell references hashed chunk names from `index.html`, so a shell tab that's still open
during a `--delete` sync can request an old hash — hard-reload to re-fetch the shell.

---

### Option B — Update directly on the server

**1. SSH as the deploy user:**

```bash
ssh deploy@example.net
```

**2. Pull the change (pin + committed assets arrive together):**

```bash
cd /opt/phlix-hub
git fetch origin
git checkout master
git pull origin master
```

**3. Rebuild the web-ui (only needed if you changed ui code without committing the rebuilt
bundle — the normal path is Option A / CI building, then git pull):**

```bash
set -a && . /etc/phlix-hub.env && set +a   # export env for the shell (unit reads it itself)
cd /opt/phlix-hub/web-ui
NPM_CONFIG_USERCONFIG=/dev/null npm ci
npm run build
```

**4. Commit the new assets (recommended — the bundle lives in git):**

```bash
cd /opt/phlix-hub
git add public/assets/app/
git commit -m "chore(hub): rebuild web-ui assets"
git push
```

**5. Restart the service — do NOT hand-kill the daemon:**

```bash
sudo systemctl restart phlix-hub
```

The unit (installed by `scripts/install.sh`) manages the Workerman master, its env file, and an
`ExecStartPre` free-ports gate across `8800/8802/8803/8804/8805/2206` (installer defaults — each
relay port is env-overridable via `HUB_*_PORT`; move one and update the unit's gate to match). The old manual
`ps | kill` / `pkill -f` / `nohup php start.php start` flow bypasses all of that — it races the
free-ports gate, drops the restart backoff, and runs a daemon you then have to babysit. If the
host is *not* systemd-managed, the blessed foreground form is
`set -a && . /etc/phlix-hub.env && set +a && php start.php start` (or `start -d` to daemonize;
`php start.php status` to observe).

## Hub Health Check

```bash
curl -s http://localhost:8800/health
```

Response carries `status` (`ok` | `unhealthy`), `service`, `version` (currently `0.5.0` — see the
`VERSION` file), package versions, a Unix timestamp, and since S312 a `maintenance` object
(`maintenance.status` carries `degraded` heartbeats even while the probe verdict stays `ok`):

```json
{"status":"ok","service":"phlix-hub","version":"0.5.0","timestamp":…,"maintenance":{…}}
```

## Verifying the Update

**1. Check chunk hashes changed:**

```bash
ssh deploy@example.net "ls -la /opt/phlix-hub/public/assets/app/assets/index-*.js"
```

**2. Verify the Q-key shortcut (ui player smoke):**

- Open DevTools (F12) → **Network** tab → check "Disable cache" → reload the player page
- Press **Q** during playback
- Should see the Quality menu (transcoded) or a "Direct Stream" toast (direct)

**3. Check hub workers are running:**

```bash
ssh deploy@example.net "ps aux | grep 'phlix-hub-http' | grep -v grep | wc -l"
# Should show at least HUB_WORKERS worker lines plus the master
```

## Troubleshooting

### "No JWT secret configured" / placeholder refusal at boot

The hub requires a real `HUB_JWT_SECRET` in `/etc/phlix-hub.env`. Since R14-08 the pre-flight
also **exits 1 on documented placeholder literals** — a copied `CHANGE-ME…` value used to boot
silently and mint tokens under a publicly-guessable key. Fix:

```bash
echo "HUB_JWT_SECRET=$(openssl rand -hex 32)" | sudo tee -a /etc/phlix-hub.env
sudo systemctl restart phlix-hub
```

(Keep the value stable — rotating it invalidates every issued token.)

### Hub workers not responding

```bash
curl -s http://localhost:8800/health
journalctl -u phlix-hub -n 50 --no-pager
tail -20 /opt/phlix-hub/.logs/error-$(date +%Y-%m-%d).log
```

### Port already in use on restart

The unit's `ExecStartPre` waits for `8800/8802/8803/8804/8805/2206` to free (the installer's
values — env-moved `HUB_*_PORT` ports need the gate updated to match), so a restart that
hangs there usually means a **stray process outside systemd** (leftover from the old manual
flow). Find it with `ss -ltnp | grep -E ':(8800|8802|8803|8804|8805|2206)'`, stop the stray
properly (`php start.php stop` from `/opt/phlix-hub` with the env sourced), then
`sudo systemctl restart phlix-hub`.

### TDZ / "can't access lexical declaration before initialization"

Same root cause class as phlix-server. The error appears in a `.vue` component when a `const` is
accessed before its declaration line is evaluated. Fix: move the `const` declaration **before**
the code that triggers it (e.g., before an `{ immediate: true }` watch that calls a function
using that `const`).

## Hub vs Server — Key Differences

| Item | phlix-server | phlix-hub |
|------|-------------|-----------|
| Code path | `/var/www/phlix/` | `/opt/phlix-hub/` |
| Web assets | `/var/www/phlix/public/assets/app/assets/` | `/opt/phlix-hub/public/assets/app/assets/` |
| HTTP port | 8096 | 8800 |
| Hub relay port | 8802 (outbound tunnel client → hub) | — (this IS the hub; `:8802` is the server-facing tunnel listener) |
| Env file | `/etc/phlix/env` | `/etc/phlix-hub.env` |
| Database | `phlix` (MySQL) | `phlix_hub` (MySQL) — separate DB |
| Profile management | Has `UserProfileManager` | Delegates to server |
| Static asset serving | Via CDN/public proxy | Via hub Workerman (committed `public/assets/app/`) |
